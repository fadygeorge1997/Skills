# Data Model: UX & Product Design Agent

**Feature**: 001-ux-design-agent
**Date**: 2026-03-13

## Overview

The UX Design Agent is a skill-based system — not a database-backed application. Its "data model" consists of structured markdown files that the agent reads, writes, and validates. This document defines the schemas for those files.

## Entity: Phase

Represents one of the 7 workflow stages the agent guides users through.

**Persisted in**: `ux/phase-status.json` (in consuming project)
**Referenced by**: All phase-specific skills, master SKILL.md orchestrator

### Schema

```json
{
  "currentPhase": 1,
  "phases": [
    {
      "id": 1,
      "name": "Discovery & Research",
      "slug": "discover",
      "command": "/ux.discover",
      "status": "complete|in-progress|not-started",
      "dodChecklist": {
        "total": 9,
        "completed": 9,
        "items": [
          {
            "id": "d1",
            "description": "Stakeholder alignment on objectives",
            "status": "done|pending|skipped",
            "evidence": "Link or note",
            "skippedReason": null
          }
        ]
      },
      "artifacts": [
        {
          "type": "research-plan",
          "path": "ux/research/research-plan.md",
          "created": "2026-03-13",
          "evidenceLevel": "assumption|observed|measured"
        }
      ],
      "completedAt": "2026-03-15T10:30:00Z"
    }
  ],
  "context": {
    "mode": "mvp|growth|enterprise",
    "domain": "fintech|saas|healthcare|ecommerce|other",
    "teamSize": "solo|small|mid|large",
    "inferredFrom": "explicit|project-signals"
  },
  "lastUpdated": "2026-03-15T10:30:00Z"
}
```

### State Transitions

```
not-started → in-progress   (user invokes phase command)
in-progress → complete      (all DoD checklist items done or explicitly skipped with reason)
complete → in-progress      (user re-opens phase for iteration)
```

### Validation Rules

- `currentPhase` MUST be between 1 and 7.
- A phase MUST NOT be marked `complete` if any DoD item is `pending` (must be `done` or `skipped` with reason).
- `context.mode` defaults to `mvp` if not set explicitly or inferred.
- Phase advancement warnings trigger if DoD items are skipped (non-blocking but logged).

## Entity: Evidence Tag

An inline annotation classifying the confidence level of a claim. Used across all artifact types.

**Persisted in**: Inline within artifact markdown content
**Referenced by**: Phase DoD validation, cross-phase traceability

### Tag Types

| Tag | Usage | Example |
|-----|-------|---------|
| `[EVIDENCE: source]` | Claim backed by specific research | `[EVIDENCE: interview #3, user quote about friction]` |
| `[ASSUMPTION: reason]` | Hypothesis requiring validation | `[ASSUMPTION: inferred from segment behavior patterns]` |
| `[MEASURED: metric, source]` | Quantified observation from analytics | `[MEASURED: D7 retention = 42%, Mixpanel dashboard]` |
| `[CONTRADICTION: src1 vs src2]` | Conflicting data requiring resolution | `[CONTRADICTION: interviews say X, analytics show Y]` |

### Evidence Level ↔ Tag Mapping

The `evidenceLevel` field in artifact headers uses short labels; the inline tags use bracketed format. They map as follows:

| Header Value | Inline Tag Format | Meaning |
|-------------|-------------------|---------|
| `assumption` | `[ASSUMPTION: reason]` | Hypothesis requiring validation |
| `observed` | `[EVIDENCE: source]` | Backed by direct research observation |
| `measured` | `[MEASURED: metric, source]` | Quantified from analytics data |

The `[CONTRADICTION: src1 vs src2]` tag has no header equivalent — it is always inline within artifact content.

### Validation Rules

- Every persona behavior MUST have at least one evidence tag.
- Proto-personas MUST have ALL fields tagged `[ASSUMPTION]`.
- Journey map stages with no direct evidence MUST be tagged `[ASSUMPTION: gap in research]`.
- Contradictions MUST include resolution recommendations (not just flagged).
